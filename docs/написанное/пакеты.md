# Справочник по пакетам

## `core` — правила

Ни сети, ни времени, ни `Math.random`. Всё случайное идёт через
сериализуемое состояние ГПСЧ.

| Модуль | Что внутри |
|---|---|
| `types.ts` | доменная модель, события, `RuleError` |
| `rng.ts` | `mulberry32`; состояние — одно число |
| `cards.ts` | 30 Чар и 8 Архимагов: имена, эпохи, цены |
| `setup.ts` | масштабирование, Порог, создание партии, драфт |
| `resolve.ts` | Пульс, Плетение, Резонанс, Возврат, Строительство |
| `effects.ts` | эффекты карт + честный список ждущих расширения |
| `standing.ts` | предзаявки §8: три группы, порядок, условия |
| `score.ts` | Схождение, смена эпохи, финальный подсчёт |

**Ключевые функции.** `createGame`, `resolvePulse`, `resolveWeaving`,
`resolveBuilding`, `resolveConvergence`, `advanceEpoch`, `finalScores`.

**Точка расширения.** Эффект, которому нужны новые данные от игрока,
добавляется так: поле в `WeavingAction` или `BuildingAction` → валидация в
`resolve.ts` → функция в `effects.ts` → вызов в точке разрешения → удалить
строку из `NEEDS_PLAYER_INPUT`. Тест честности разметки не даст забыть
последний шаг.

## `protocol` — граница

| Модуль | Что внутри |
|---|---|
| `messages.ts` | сообщения клиента и сервера, zod-схемы, `parseClientMessage` |
| `view.ts` | `PlayerView`, `LobbyView`, `PublicGameView` |
| `history.ts` | разбор сырых событий раунда в читаемый пересказ |

Каждое входящее сообщение валидируется zod: заявка приходит из браузера, а
браузер — не наш код. Отвергаются отрицательные и дробные величины,
несуществующие узлы, абсурдные числа и слишком длинные имена.

## `server` — комнаты и хранение

| Модуль | Что внутри |
|---|---|
| `project.ts` | редактированные проекции — самое важное место |
| `room.ts` | правила комнаты: фазы, готовность, уведомления |
| `rooms.ts` | реестр, кэш активных, подъём из базы, уборка |
| `store.ts` | весь SQL; переход на Postgres переписывает только его |
| `server.ts` | транспорт: разобрать сообщение, найти комнату, позвать метод |
| `main.ts` | точка входа, фоновая уборка, обработка сигналов |

### Проекции

Собираются **с нуля**, а не вычищаются из состояния: вычитание однажды
забудут, и чужая стопка уедет в браузер соперника. Перечислено только то,
что показывать можно.

| Данные | Кому видно |
|---|---|
| стопки маны | никому до Раскрытия; после — всем через историю |
| своя отправленная ставка | только владельцу |
| мана, эссенция по цветам, Скверна, число Чар | всем |
| Порог, усиленные узлы, рынок | всем |
| готовность соперника | всем, но только факт |
| Порог следующего раунда | Компасу и Провидцу |
| усиленные узлы следующего раунда | Провидцу |
| на скольких узлах стоят соперники | Оку, без сумм |
| своя рука драфта | только владельцу |

Семь тестов проверяют это со стороны получателя, включая поиск запрещённых
ключей на любой глубине.

### Очередь мутаций

Все изменения комнаты идут через последовательную очередь: два «Готово» в
одну миллисекунду обрабатываются строго по одному, и условие «все готовы»
проверяется после каждого.

### Хранение

Схема §9, переложенная на SQLite: `uuid → TEXT`, `jsonb → TEXT`,
`timestamptz → INTEGER`, частичный индекс по активным комнатам. Комната и
снимок пишутся одной транзакцией.

Снимок пишется после разрешения фазы, поэтому перезапуск посреди Плетения
потерял бы уже отправленные ставки. Для этого существует журнал `room_actions`
из §9: при подъёме комнаты заявки текущей версии восстанавливаются из него.

## `sim` — баланс

| Модуль | Что внутри |
|---|---|
| `policy.ts` | агент: случайный и эвристический |
| `play.ts` | прогон партии и сбор наблюдений |
| `metrics.ts` | свод метрик §11 |
| `cli.ts` | отчёт |
| `debug.ts` | сырой дамп раундов — когда сводка врёт |

```bash
pnpm sim --players 8 --games 10000 --buy-rate 0 --risk 0.4
```

Агрессия агента вынесена в `--risk` сознательно: подкручивать её, пока цифры
не сойдутся с целевыми, значит подгонять ответ под ответ.
