# Архитектура

## Три принципа

Взяты из §1 спецификации разработки и соблюдены буквально.

**Сервер — единственный источник истины.** Клиент не получает чужих данных
вообще. Не «получает и прячет на фронте», а не получает: проекция собирается
с нуля из того, что показывать можно.

**Логика игры — чистая функция.** Всё разрешение раунда живёт в
`resolveRound(state, actions) → newState` без побочных эффектов, сети и
времени. Отсюда тесты без моков и симуляция баланса на тысячах партий.

**Партия асинхронна.** Без таймеров сессия перестаёт быть сессией: кто-то
вернётся через сутки. Состояние живёт в базе и переживает перезапуск.

## Пакеты

```
packages/
  core/       чистая логика: типы, resolveRound, карты, эффекты, предзаявки
  protocol/   типы сообщений, zod-схемы, проекции, разбор истории
  server/     комнаты, сокеты, SQLite, уведомления
  sim/        агент и отчёт по балансу
  client/     React, пока хот-сит
```

Зависимости строго однонаправленные:

```
core  ←  protocol  ←  server
  ↑                      
  ├── sim
  └── client
```

`core` не импортирует **ничего**, кроме самого себя и `node:`-модулей. Это
проверяется тестом `architecture.test.ts`, а не соглашением: спецификация
предупреждала, что иначе правило протухнет за месяц. Тот же тест следит,
что в ядре нет `Math.random` и нет обращений ко времени — иначе партия
перестанет воспроизводиться из лога.

## Почему такой стек

Игровой движок не нужен: это карточки и жетоны, DOM справляется. TypeScript
на обеих сторонах ради общих типов протокола — это главная экономия.
Vitest, потому что ядро тестируется без сети.

Одно отступление от спецификации: **SQLite вместо PostgreSQL**, причины —
в [журнале решений](решения.md). Драйвер встроен в Node 24, поэтому у
развёртывания нет ни одной нативной сборки.

## Данные

Состояние партии — один сериализуемый объект `GameState`. Внутри всё,
включая состояние генератора случайных чисел: одно число, `mulberry32`.
Из-за этого партия воспроизводится из лога побайтово, и на этом стоит
и тест детерминизма, и симуляция.

Два отступления от типов спецификации:

- `ready` и `pendingActions` — массив и объект вместо `Set` и `Map`. Спека
  сама предупреждала, что они не сериализуются в JSON; проще не создавать
  проблему, чем конвертировать на границе.
- у `BuildingAction` появилось поле `pay`. Цена платится эссенцией любых
  цветов — значит, игрок выбирает, какими именно, и этот выбор решает, кому
  достанется большинство на Схождении. В спецификации поля не было.
